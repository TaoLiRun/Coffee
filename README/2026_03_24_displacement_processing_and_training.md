## How the model is trained

### 1. Load and filter the raw inputs

`main.py` loads:

- `order_result.csv`
- `non_uni_store_closures.csv`
- `no_push_members.csv`
- `member_result.csv`
- `closure_pair_registry.csv`

Then it:

- keeps only closures with `closure_start >= 2020-09-01`
- keeps only closures present in the registry with `status == kept`
- identifies treatment and control members for each closure
- filters `df_order_full` down to the union of those panel members

### 2. Build two panels

The script builds:

- `panel`: the training/evaluation panel
- `t0_panel`: the ex-ante scoring panel used after training

For the training panel:

- periods `-4`, `-3`, `-2`, `-1` are pre-closure windows of length `D = closure_duration_days`
- control group period `0` covers the closure window and is used only for evaluation
- closures without enough history are skipped

### 3. Build or load cached features

If a matching feature cache exists and `--rebuild-feature-cache` is not used, the pipeline loads:

- `features_df`
- `t0_features_df`

Otherwise it:

1. builds or loads the filtered push-event cache
2. computes features for the training panel
3. computes features for the `t0` panel
4. saves both feature matrices back to cache

The engineered features include:

- closure timing features
- encoded demographics
- purchase frequency and recency
- order counts and spend
- habit and regularity features
- day-of-week behavior
- basket size and category breadth
- store loyalty measures
- order-level aggregates
- push features when `push_features.enabled` is `true`

### 4. Select training columns

The model excludes identifiers and non-feature bookkeeping columns such as:

- `member_id`
- `dept_id`
- `closure_start`
- `closure_end`
- `period`
- `group`
- `label`
- `is_treated`
- `period_start`
- `period_end`
- closure-event descriptors such as `closure_length_days` and `closure_duration_days`

All remaining numeric columns are used as `feature_cols`.

### 5. Audit label balance

Before training, the pipeline writes `label_balance_audit.csv` with:

- the closure duration
- the slice name
- row count
- positive-label count
- positive-label rate

The slices are:

- `train` for `period <= -2`
- `eval_pre_treatment` for treatment rows at `period == -1`
- `eval_pre_control` for control rows at `period == -1`
- `eval_during` for control rows at `period == 0`

### 6. Fit one XGBoost model per closure duration

For each unique `closure_duration_days = D`, the script:

1. subsets `features_df` to duration `D`
2. trains on rows with `period <= -2`
3. evaluates on:
   - `period == -1`
   - control rows with `period == 0`
4. saves the duration-specific model artifacts
5. scores the matching `t0_features_df` slice and appends those scores to `displacement_scores_t0_ex_ante.csv`

The XGBoost settings come from `src/displacement_classification/config.json`:

- `max_depth = 6`
- `eta = 0.1`
- `objective = binary:logistic`
- `eval_metric = auc`
- `tree_method = hist`
- `num_boost_round = 500`
- `decision_threshold = 0.5`

If CUDA is available, the code sets `device = "cuda"`. Otherwise it trains on CPU.

## Practical notes

- `train_displacement_model.log` can contain two `Computing features (vectorized)...` sections in a single run because `compute_features_for_panel()` is called once for `panel` and once for `t0_panel`.
- Seeing `push_events_filtered_<hash>.parquet` in the cache does not mean feature computation is finished. That parquet caches only the filtered push rows; the feature-matrix cache is written later.
- If the raw order data, member data, or closure inputs are refreshed, rerun with `--rebuild-feature-cache` so the cached feature matrices are regenerated against the new upstream inputs.
